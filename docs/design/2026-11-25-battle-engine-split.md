# 전투 엔진 분리 설계 (2:2 AI 대전 준비)

작성일: 2026-11-25 · 담당: 영인(서버 전투 로직)

> **실행 방식 변경 (2026-11-25):** 영인이 잠시 B(복사)로 바꿨다가 C(엔진 분리)로 다시 정했다. 녹화 기준을 만든 뒤에는 단계마다 빌드만 확인하고, 테스트 전체·녹화 비교·검토는 마지막에 한 번 한다(영인 요청). 단계별 커밋은 그대로 남겨 녹화가 다르면 커밋을 거슬러 찾는다.

## 1. 왜 하는가

다음 기능은 **2:2 AI 대전**(플레이어 2명이 한 편이 되어 AI와 더블배틀, 연승 도전, 랭킹)이다. 그런데 지금 서버는 `RoomManager` 클래스 하나가 로비·방·1:1 턴 진행·기술 효과를 모두 맡고 있고(13개 파일, 약 4,000줄), 전투 코드 전체가 "한 편 = 플레이어 한 명 = 출전 포켓몬 한 마리"를 전제로 짜여 있다.

- `BattleSide`가 편, 출전 자리, 플레이어를 한 객체에 섞어 담고 있다. (`Player` 하나, `Current` 하나)
- `side.Current`를 쓰는 곳이 130군데, 상대를 `GetOther(room, side)` 하나로 구한다.
- 기술 효과 코드가 `side.Player.QueueMessage`로 플레이어에게 직접 메시지를 보낸다. AI 편에는 플레이어가 없고, 2:2의 우리 편에는 두 명이 있다.

2:2 코드를 따로 두면서도 기술 효과는 1:1과 한 벌로 유지하려면, 전투 규칙(엔진)을 방·네트워크에서 떼어내고 한 편에 여러 자리를 다룰 수 있게 바꿔야 한다. 이 문서는 그 준비 작업만 다룬다. 2:2 대전 자체는 별도 설계로 이어서 정한다.

## 2. 목표 / 하지 않을 것 / 실패로 보는 것

**목표**
- 전투 규칙을 `Server/scripts/Battle/`의 `Battle` 클래스로 옮긴다. 1:1과 2:2가 같은 엔진을 쓴다.
- 엔진이 한 편에 자리 여러 개, 플레이어 여러 명(또는 AI)을 다룰 수 있게 한다. 1:1은 "편마다 자리 1개, 플레이어 1명"으로 동작한다.
- 테스트를 저장소 `tests/`로 옮겨 팀원 누구나 한 줄로 돌릴 수 있게 한다.

**하지 않을 것**
- 1:1의 동작·메시지·프로토콜 변경. 클라이언트는 이 작업에서 한 줄도 바뀌지 않는다.
- 2:2 기능(대상 선택, 범위 기술 0.75배, AI, 연승, 랭킹, 더블 화면). 다음 프로젝트에서 한다.
- 클라이언트 폴더 정리. 클라이언트는 2:2를 만들 때 `Client/scripts/Double/`을 추가하면서 필요한 만큼만 나눈다. (SHJ 팀원이 연출 작업을 많이 하는 곳이라 지금 옮기면 충돌만 커진다.)
- 기술 버그 수정이나 리팩터링 "김에" 하는 개선. 발견하면 따로 적어 두고 나중에 한다.

**실패로 보는 것** (돌아가더라도)
- 1:1에서 같은 상황의 로그·결과가 이전과 한 글자라도 달라짐.
- 팀원이 작업 중이던 코드가 대규모 충돌로 날아감.
- 한 단계가 너무 커서 main에 오래 못 합쳐지고 갈라진 채 남음.

## 3. 제약

- SHJ 팀원이 같은 서버 전투 파일(`RoomManager.*.cs`)을 자주 고친다. 파일을 옮기는 단계는 짧게 끝내고 바로 main에 합친다.
- 커밋·PR에는 영인 계정만 올라간다. (Claude 표기 없음)
- .NET 10, 기존 `roomsLock` 하나로 잠그는 방식 유지. 엔진은 잠금 안에서만 호출된다.
- 전투에 무작위가 많다(`Random.Shared` 31곳). "동작이 같다"를 확인하려면 무작위를 고정할 수 있어야 한다.

## 4. 접근 방법

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 같이 쓰기 | `RoomManager` 안에서 기술 효과가 "맞는 자리"를 받게 고침. 2:2 전용만 `Double/` | 변경량 중간 | `RoomManager`가 계속 모든 일을 맡아 비대함. 2:2 코드가 결국 같은 클래스에 섞임 |
| B. 통째로 복사 | 전투 코드를 `Double/`에 복사 | 1:1 무변경 | 약 4,000줄 중복. 기술 수정이 한쪽에만 반영되어 1:1과 2:2가 점점 달라짐 |
| **C. 엔진 분리 (선택)** | 전투 규칙을 `Battle/`로 떼고, 1:1(`Single/`)·2:2(`Double/`)·로비(`Lobby/`)가 엔진을 씀 | 기술 효과 한 벌, 모드별 폴더 분리, 팀원 간 파일 충돌 감소, 엔진을 네트워크 없이 테스트 가능 | 초기 작업이 가장 큼. 옮기는 순간 팀원 작업과 충돌 위험 → 단계로 나누고 녹화 비교로 검증 |

영인이 C를 골랐다(2026-11-25). 기술 효과를 한 벌로 유지하면서 모드별 코드를 폴더로 나누고 싶다는 두 요구를 모두 만족하는 방법은 C뿐이다.

## 5. 설계

### 5.1 최종 서버 폴더 구조

```
Server/scripts/
  Battle/            전투 규칙. 네트워크·방을 모른다. 1:1과 2:2 공용
    Battle.cs          전투 하나의 상태(날씨·필드·트릭룸·턴 순서 등)와 턴 진행
    Battle.Attack.cs / .Copy.cs / .Effect.cs / .Field.cs / .Heal.cs / .Power.cs
    Battle.Protect.cs / .Stats.cs / .Status.cs / .Switch.cs     (지금 RoomManager.*.cs의 기술 효과)
    Battle.Views.cs    BattleView·PokemonView 만들기 (GetPokemon, GetMove, SendBattleState)
    BattleSide.cs      편: 편 전체 효과
    BattleSlot.cs      자리: 출전 포켓몬과 이번 턴 행동 (2단계)
    BattlePlayer.cs    플레이어: 접속(또는 AI), 맡은 포켓몬, 메가진화 사용 여부 (2단계)
    BattlePokemon.cs, BattleMoveSlot
  Single/            1:1 대전: 팀 선택 검증, 행동 받기, 안내(CHOOSE_ACTION 등), 타이머, 결과·재도전
  Double/            (다음 프로젝트) 2:2 AI 대전
  Lobby/             닉네임, 방 목록, 방 만들기·입장·준비·나가기 (지금 RoomManager.cs 앞부분)
  GameData.cs, ClientSession.cs, States/ ...   (그대로)
```

`RoomManager`는 로비와 방 관리만 남고, 1:1 전투 진행은 `Single/`의 클래스가 맡는다. 정확한 클래스 이름은 구현하면서 정한다(빌더 재량). 단, 엔진 클래스 이름은 `Battle`로 한다.

### 5.2 엔진과 모드의 경계

엔진(`Battle`)은 "입력을 받으면 다음 입력이 필요할 때까지 전투를 진행"하는 객체다.

- **상태:** 지금 `GameRoom`에 있는 전투 상태(`Weather`, `TerrainTurns`, `TrickRoomTurns`, `GravityTurns`, `TurnQueue`, `TurnNumber`, `LastExecutedMove` 등)는 `Battle`로 옮긴다. `GameRoom`에는 방 정보(방장·참여자·팀 선택·재도전·마감 시각)와 `Battle? Battle`만 남는다.
- **입력:** 모드 쪽이 검증을 마친 행동을 엔진에 넘긴다(기술 슬롯·메가진화 폼·교체 번호). 검증 로직 중 "이 기술을 지금 쓸 수 있나"(`MoveBlockedBy`, `MustStruggle`, `GetMegaForms`)는 규칙이므로 엔진에 두고, 모드는 그 결과로 ERROR 메시지를 보낸다.
- **진행 결과:** `TryResolveTurn`·`ContinueTurn`이 지금은 끝에서 `StartTurn`·`SendPrompts`·`Deadline`을 직접 부른다. 이것을 엔진이 진행 결과(행동 선택 대기 / 턴 도중 교체 대기 / 쓰러진 자리 교체 대기 / 전투 끝과 승패)를 돌려주는 방식으로 바꾸고, 안내 메시지 전송과 타이머 설정은 모드가 한다.
- **출력:** 엔진은 `ClientSession`을 직접 부르지 않는다. 모든 메시지는 "이 편을 보는 사람들"에게 보내는 메서드 하나(`Send(side, message)`)를 거친다. 1:1에서는 각 편을 보는 사람이 1명, 2:2에서는 우리 편 2명·AI 편 0명이 된다. 시점이 다른 로그(`Log(actor, mine, theirs)`)도 같은 길로 나간다.
- **무작위:** 엔진은 `Random.Shared` 대신 전투마다 하나씩 갖는 `Random`을 쓴다. 서버 실행 인자로 시드를 주면(테스트 전용, 예: `Server.exe 5000 --seed 42`) 그 시드로 만든다. 시드가 없으면 지금처럼 매번 다르다. 시간 초과 때 기술을 대신 고르는 무작위(`RoomManager.Timer.cs`)도 그 전투의 `Random`을 쓴다.

### 5.3 편·자리·플레이어 (2단계)

지금 `BattleSide`의 필드를 셋으로 나눈다.

| 새 객체 | 옮겨 갈 것 |
|---|---|
| `BattleSide` 편 | 리플렉터·빛의장막·순풍·흰안개·주술·신비의부적, 패스트가드·와이드가드·마룻바닥세워막기·트릭가드, 압정뿌리기·독압정·스텔스록·끈적끈적네트, 이번·지난 턴에 쓰러졌는지(원수갚기), 팀 전체 포켓몬 목록 |
| `BattleSlot` 자리 | 출전 중인 팀 번호(`Active`/`Current`), 이번 턴 행동(`ChosenMove`·`ChosenMegaForm`·`ChosenSwitch`·`Struggling`·`TurnActor`), 턴 도중 교체·배턴터치·쓰러져서 교체(`SwitchingMidTurn`·`BatonPassing`·`MustSwitch`), 희망사항, 미래예지·파멸의소원, 치유소원·초승달춤 (본가에서 모두 "그 자리"에 걸리는 효과) |
| `BattlePlayer` 플레이어 | 접속(`ClientSession?`, AI면 null), 맡은 포켓몬(팀 번호 목록), 메가진화를 썼는지(`HasMegaEvolved`. 2:2 규칙이 "플레이어마다 1번"이라 편이 아니라 플레이어에 둔다) |

- 엔진의 기술 처리(`ExecuteMove`, `CalculateDamage`, `UseStatusMove` …)는 `BattleSide` 대신 **자리**를 받는다: "쓰는 자리"와 "맞는 자리".
- `GetOther(room, side)`는 "상대 편"과 "고른 대상 자리"로 나뉜다. 1:1에서 대상은 언제나 상대 편의 하나뿐인 자리다.
- 교체 시 헤롱헤롱 해제처럼 "상대 포켓몬"을 가리키던 곳은 "상대 편의 모든 출전 자리"로 바꾼다. 1:1에서는 결과가 같다.
- 이 단계에서는 대상이 언제나 하나다. 범위 기술(파도타기·지진)과 대상 선택은 2:2 프로젝트에서 DB에 기술 대상 정보를 넣은 뒤 추가한다.
- 1:1 구성: 편 2개 × 자리 1개 × 플레이어 1명. 메가진화 "한 전투에 한 번"은 플레이어가 1명이라 지금과 같다.

### 5.4 테스트

지금 테스트(Python, 서버를 실제로 띄워 소켓으로 대전)는 영인 PC의 임시 폴더에만 있어 언제든 지워질 수 있다.

- 저장소 `tests/`로 옮긴다: 공격·필드·위력·효과·상태이상·교체·6세대 규칙·실패 기술·메가진화(X·Y 포함)·메타몽·편 효과 등. 실행은 `python tests/run_all.py` 한 줄(서버 빌드 → 모든 묶음 실행 → 통과·실패 요약).
- 옮기면서 지금 알려진 실패 3개(테스트용 포켓몬·기술 선택이 DB 변경으로 어긋난 것)와 PP 도입으로 깨진 부분을 고쳐 **전부 통과하는 상태**에서 시작한다. 오래돼 최근에 안 돌린 묶음(공격·필드·위력)도 이때 다시 맞춘다.
- **녹화 비교 테스트:** 시드를 고정한 대본 대전 여러 개를 돌려 서버가 보낸 메시지를 전부 저장한다(분리 전 기준). 각 단계 후 같은 대본을 다시 돌려 **메시지가 한 글자도 다르지 않아야** 한다. "동작을 바꾸지 않았다"를 사람 눈이 아니라 비교로 증명한다.

### 5.5 진행 순서 (단계마다 main에 PR 하나)

0. **준비:** 테스트를 `tests/`로 옮기고 전부 통과시키기 + 엔진 무작위를 전투별 `Random`으로 바꾸고 시드 인자 추가 + 녹화 기준 만들기. 동작 변화 없음.
1. **옮기기:** 전투 규칙을 `Battle/`로, 로비를 `Lobby/`로, 1:1 진행을 `Single/`로 옮긴다. 엔진·모드 경계(5.2)를 세운다. 녹화 비교 통과.
2. **편·자리·플레이어 나누기:** 5.3대로 바꾼다. 녹화 비교 통과.

팀 작업 순서:
- 1단계 시작 전에 SHJ 팀원이 진행 중인 서버 전투 작업을 main에 먼저 합친다.
- 1단계는 짧게 끝내 바로 main에 합치고, 팀원에게 "기술 효과는 이제 `Server/scripts/Battle/`에 있다"고 알린다. README의 파일 위치 안내도 함께 고친다.
- 1단계의 파일 이동은 **이동만 하는 커밋**(`git mv`, 내용 변경 없음)과 **내용을 고치는 커밋**을 나눈다. 그래야 git이 파일 이름 변경을 알아보고, 팀원이 옛 경로(`RoomManager.Status.cs` 등)에서 고친 내용을 병합할 때 새 경로로 따라가 적용해 준다.
- 단계 사이에는 main을 자주 받아 와 갈라짐을 줄인다.

## 6. 남은 것

**영인과 정하지 않고 설계자가 정한 것** (틀리면 고친다)
- 테스트는 지금처럼 Python으로 둔다. C# 테스트로 다시 쓰는 것은 양이 커서 하지 않고, README에 Python 설치·실행 방법을 적는다.
- 설계 문서 위치는 `docs/design/`.
- 팀 선택 검증(3마리, 기술 4개, 막힌 종)은 1:1과 2:2가 같이 쓰므로 모드 폴더가 아닌 공용 위치에 둔다.

**빌더 재량**
- `Single/`·`Lobby/` 클래스 이름과 파일 나누는 단위. 서버 `States/InGameState.cs`가 명령을 어느 객체로 넘길지.
- 진행 결과를 돌려주는 형태(열거형, 레코드 등).
- 녹화 대본의 개수와 구성. 단, 메가진화·턴 도중 교체·2턴 기술·날씨·설치기·변신·발버둥·타임아웃은 반드시 포함.

**다음 프로젝트(2:2 AI 대전)에서 정할 것**
- 기술 대상 정보(상대 하나 / 상대 모두 / 자기 편 포함 / 아군)를 DB에 추가하는 방법 (`build_db.py`, DB 담당 팀원과 협의).
- AI 팀 구성 규칙의 세부, AI의 기술·대상 선택, 교체 시점, 연승·랭킹 저장, 팀원이 나갔을 때 처리, 더블 화면 배치.
